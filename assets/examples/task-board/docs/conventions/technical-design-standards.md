# 技术方案编写规范

## 范围与触发

跨 app/web 模块、接口、数据或失败恢复变化写 docs/designs/<topic>.md；局部可逆修改在需求/Issue 简写适用问题。当前没有长期 ADR 决策，不强制新增 ADR。具体方案在 tasks.md，本文件定义写法。

## 八个问题与规则

回答涉及哪些模块、各处改什么、数据流、接口输入输出、失败处理、兼容影响、验证方法、出问题如何恢复。按影响写实路径与职责，不适用给理由；不靠“遵守规范”省略答案。拟方案标计划，落地后写实际差异与结果；目录和依赖遵循 directory-structure，长期决策历史保留替代链。

## 正确例与反例

正确：app/http.py 解析 POST JSON，service 校验标题，storage 参数化写入；返回 201 与任务对象，ValueError 返回 400 且不写入。错误：“新增 create 功能、完善异常处理”，无法指导文件落位与失败判断。

## 检查

对照每条 AC，确认八问有答案、路径可达、依赖方向明确、接口调用方与恢复可执行。没有迁移/部署时写本机代码恢复，恢复与交付步骤以项目真实运行能力为依据。

正确：筛选改 http 参数解析、service 校验、storage 查询、web/api 和页面状态，schema 不变；契约变化需要独立 list-filter 方案。错误：只写“增加筛选逻辑”，无法决定文件归属与失败恢复。

### 本文件检查如何判定

静态/文本：使用根入口真实检查命令定位语法或引用线索，不能证明规则语义。
语义审查：对照本文件规则阅读受影响实现、调用方和有效 AC，列已读边界。
行为测试：根目录 unittest 覆盖协议/数据库/输入场景；新增验收映射到具体需求与测试，不推断所有异常已覆盖。
人工 UI：页面相关规则按 UI 规范记录视口/键盘/状态操作；纯目录、写法或 SQL 规则不适用视觉检查。实际执行状态单列。
