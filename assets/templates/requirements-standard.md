# 需求写作规范

> 填入项目需求位置与既有格式；本文件教如何写，具体需求用 requirement.md 产物模板。删除提示。

## 存放与粒度

需求保存于（真实目录/Issue 系统），每个行为主题一份。按影响选写法：跨模块或影响数据/权限/金额/兼容的需求写完整背景、范围、规则、异常与 AC；单模块行为变更写简化目标、规则和 AC；文案/局部可逆小修写一句话加验收条件，沿用现有 Issue 或对话即可。关键歧义先澄清，其他不阻碍执行的未知标待确认。

## 必须写清

- 谁在什么场景遇到什么问题；目标与不在本次范围的内容。
- 输入、前置条件、允许/拒绝行为、成功结果；异常、权限、重复/并发及兼容边界按实际风险选择。
- 每条 AC 使用稳定标识与可观察输入/结果；避免“体验良好”“功能正常”等不能验证的措辞。
- 未决定问题单列，不能把代理猜测写为批准事实；用户明确新要求作为修订依据，保留影响与旧/新 AC 对应。
- 交付区分计划、已实现、已验证；AC 链接实际实现/测试或人工检查证据，不虚构通过结果。

## 写法小例（教学，替换为项目例子）

`AC-1：用户有取消权限且订单未发货时，提交取消后状态成为 cancelled；重复提交返回同一结果，不重复退款。`

反例：`支持订单取消，运行正常。` 缺少状态、权限、重复行为与可观察结果。

## 检查

对照 AC 检查成功/拒绝/边界输入是否可执行、关键歧义是否已决；核对当前代码/测试与有效需求。冲突显式报告，不用改需求掩盖实现偏离。

## 检查证据的边界

为上面的每条规则选择实际适用的验证，并注明结果；不存在的工具写未配置。

| 类型 | 填写内容 | 能证明的范围 |
|---|---|---|
| 编译/lint/文本线索 | 真实命令、配置、定位结果 | 语法/静态约束或候选；文本命中不是行为证明 |
| 语义审查 | 受影响代码、调用方、规则/AC 对照 | 本次已阅读范围与判断；列未读边界 |
| 行为测试 | 输入/状态、预期结果、真实测试路径/命令 | 实际执行场景；不外推所有异常或环境 |
| 人工 UI 检查 | 页面状态、视口、键盘/焦点步骤 | 实際操作范围；无 UI 写不适用依据 |
