# 让 AI 按项目规矩写代码：从一个入口和几份具体规范开始

给 AI 一句“实现这个功能”，它往往能写出代码。但代码应该放哪里？业务逻辑能不能直接调用数据库？错误由谁转换？需求有没有说清重复操作和异常行为？功能变更以后，原来的说明还准不准？这些问题不能只靠每次对话临时补充。

`ai-project-conventions` 做的是把答案落到项目里：先生成一个完整入口，再按实际技术栈和业务需要生成几份具体规范。AI 开工时读入口，涉及某类修改时再读那一份规则；需求和设计变化后，更新对应文件。我们可以打开文件审阅，也可以把它们和代码一起提交。

## 入口先把项目讲明白

项目使用什么工具，就维护它实际读取的 `AGENTS.md` 或 `CLAUDE.md`。默认只选一个。已有双入口镜像约定时才同步两份，工具尚未确定时先保存完整的中立项目指引并标记接入待确认。

这个入口要能回答六件事：

1. **项目全景**：项目服务谁，负责哪些业务，不负责哪些业务；主要模块怎样协作，与哪些外部系统交互。
2. **架构铁律**：允许和禁止的依赖、业务/协议/数据访问的实现边界，不能破坏的状态或事务约束。
3. **真实技术栈**：语言、框架、存储、构建工具的版本口径与配置来源。声明范围、锁定版本、本机运行版本要分清。
4. **代码目录归属**：认可的目录树，每个目录装什么，新模块和新文件放哪里。测试、配置、脚本、文档和生成物也要有位置。
5. **运行和检查**：命令、工作目录、环境前提、配置来源，以及是否真正运行过。
6. **条件读取**：改语言行为读哪份规范，改页面或数据读哪份规范，具体需求与方案去哪里找。

入口不是只有“请遵守工程规范”这句话。比如下面这段已经能够影响 AI 的落位和依赖选择。

> 教学示例：假设这是一个 Go 订单 API 与 Vue 管理端；不是当前仓库事实，也没有运行该业务项目。

```text
项目：订单创建、查询、取消；支付由外部支付服务负责。
关系：HTTP 适配 → 订单用例 → Repository/Payment 接口；
      PostgreSQL 和支付适配实现这些接口，启动入口负责组装。
铁律：订单领域不得导入 HTTP 或 PostgreSQL 适配；
      外部退款不能放进数据库事务，失败转入可重试任务。
技术栈：Go 声明 1.23.0，来源 go.mod；
        Vue 声明 ^3.5.0，来源 web/package.json，实际安装看锁文件；
        开发 PostgreSQL 镜像主版本 16，生产版本尚未核实。
目录：cmd/api/ 启动；internal/order/ 规则与用例；
      internal/transport/http/ 输入与响应；
      internal/storage/postgres/ SQL 与事务；
      internal/integration/payment/ 支付适配；
      internal/jobs/ 重试调度；web/src/api/ 网络适配。
新增：订单规则放 internal/order/，不能散落在 HTTP handler；
      新领域放 internal/<domain>/，同时更新入口目录归属。
检查：根目录 go vet ./...、go test ./...；
      web/ 下 npm run typecheck、npm run build。
      这里只展示有配置来源的命令，不代表已经执行通过。
条件：Go 代码先读语言规范；模型/事务再读数据库规范；
      行为变化读具体需求和 AC；验证读测试规范。
```

完整已填教学入口在技能包的 `references/generated-example.md`。实际初始化时，代理必须读代码、清单、CI 和现有文档来填写，不能把这段例子复制成项目事实。

## 几份规范各自管一件具体的事

一个带前端和数据库的项目，可以生成这样的结构。已有文档路径优先复用；不适用的文件不生成，多语言可以按代码目录拆分。

```text
AGENTS.md                     # 或 CLAUDE.md
docs/
  conventions/
    language.md
    frontend.md
    ui.md
    database.md
    requirements.md
    technical-design.md
    testing.md
  requirements/               # 具体需求
  designs/                    # 具体方案
```

| 文件 | 写什么 | AI 什么时候读 |
|---|---|---|
| language | 命名与类型、输入校验、错误、资源、并发、依赖、格式与检查 | 修改对应语言代码 |
| frontend | 页面/组件归属、路由、状态来源、API 适配、构建边界 | 修改前端工程 |
| ui | 组件与 token 来源、加载/空/失败状态、表单、键盘、布局与视觉验收 | 修改页面或交互 |
| database | 字段含义、约束、索引依据、事务、查询、迁移兼容与恢复 | 修改模型、查询、数据访问或迁移 |
| requirements | 需求怎么写，边界怎么描述，验收怎么验证和修订 | 新增或修改业务行为 |
| technical-design | 方案要回答哪些问题，什么时候需要独立设计 | 跨模块、契约、数据或复杂取舍 |
| testing | 测试放哪里、选哪些边界、如何隔离、执行什么命令 | 修改代码和验收行为 |

前端工程和 UI 有明确分工。前端规范可以要求请求统一经过 `web/src/api/`，页面不能到处拼 URL；UI 规范则说明加载失败要展示什么、重试以后输入是否保留、键盘焦点是否可见。

语言规范也要落到真实栈。Go 项目从 `go.mod` 和 CI 核实版本，再明确 error、context、资源和 goroutine 的生命周期；Java 项目从 Maven/Gradle 的编译配置核实目标版本，再明确异常 cause、try-with-resources、线程与事务边界。不能给所有项目塞进同一套框架习惯。包内保留 Go/Java 的短例和官方资料供按需选用。

每份规范的主要内容应该是“做什么、在哪里做、一个短例、怎样检查”。例如“数据库唯一约束写进 schema”比“重视数据质量”更能指导实现；“失败、空状态必须有恢复入口”比“提升用户体验”更能验收。不要求为每条规则填一张复杂元数据表。

## 规则与具体需求、方案分开

`conventions/requirements.md` 说明需求的写法；`requirements/cancel-order.md` 才写某次取消需求。

一条可检查的验收可以是：

> AC-1：有取消权限且订单未发货时，提交有效原因后状态成为 cancelled；重复提交返回同一结果，不重复退款。

它把权限、状态、输入和重复行为写出来。实现后，把 AC 关联到实际代码、测试或人工验证，区分已实现与已验证。“支持取消，功能正常”没有提供同样的信息。

技术方案也是如此。规范要求说明现状证据、拟改路径、模块职责、契约、失败处理、兼容及验证；具体方案填入这次修改的答案。小修改可以在现有需求里写一段方案，跨模块或复杂迁移才拆独立文档。计划方案尚未落地时不能进入“当前架构”冒充事实。

默认生成不会顺手创建地图、门禁、采用记录、影响图、任务账本或 eval 文件。确实需要时，`add` 仍有对应模板；项目首先得到的是能够直接指导编码的文件。

## 项目变了，具体更新哪一份

初始化只是开始。比如新加一个支付适配目录，需要更新入口目录归属和系统关系；升级语言或改检查脚本，需要更新入口技术栈/命令以及相关语言、测试规则。

`sync` 会读取实际差异和相关代码，并按文件职责回补：

- 目录、架构、栈与命令变化，更新入口对应段落。
- 语言、前端、UI 或数据规则变化，更新那份权威规范。
- 业务行为变化，修订具体需求与 AC；需求写法本身变化才改需求规范。
- 实现方案或长期决策变化，修订具体设计或 ADR；设计写法变化才改方案规范。
- 验证方式变化，更新测试规范、实际配置和入口命令。

用户明确提出的新要求是合法修订依据，不能因为旧文档不同就一直等待。另一方面，代码偏离仍然有效的需求，应该报告实现冲突，不能偷偷改需求使它看起来一致。旧 ADR 保留替代关系，旧/新 AC 保留修订关联；未实现、未验证的部分继续明确写出来。

同步不是后台自动监听。调用 `sync`，或在开发任务交付前要求同步受影响文件，才会执行这项工作；报告要说明实际比较范围、改了哪些文件、哪些不适用、哪些仍待确认。

## 怎样开始用

在目标项目发出：

```text
$ai-project-conventions init
```

这是支持该语法的代理调用示例，不是独立终端命令。生成后先审阅入口中的项目事实、依赖方向、目录归属和命令；日常给需求时，AI 先读入口，再条件读取相关规范。

其他常用操作：`sync [git-ref]` 更新文档，`audit [git-ref]` 只读找漂移与冲突，`check` 检查结构/质量，`add` 补一种明确需要的文档。`workflow` 和 `resume` 保留为可选协作辅助，没有要求每个任务走一套抽象阶段或填任务账本。

这次技能的默认文件契约调整为 3.0.0，六类通用规则的 32 个稳定 ID 继续保留。技能可以携带核心、参考和模板到支持它的工具；客户端接入按实际配置核实。更新个人技能不会自动覆盖业务项目规范，项目仍按自己的事实与授权采用。
