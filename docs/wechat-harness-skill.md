# 让 AI 按项目规矩写代码：先把这几份文件写具体

给 AI 一句“实现这个功能”，它能很快写出代码。但业务规则放哪里？请求失败怎么处理？数据库怎样保证约束？功能变了，原来的需求和说明还准不准？这些答案需要留在项目里，供下一次开发继续使用。

`ai-project-conventions` 做的是从真实代码、配置、测试和 CI 中提取事实，写成一个项目入口和几份具体规范。人可以打开文件审阅，AI 开工先读入口，再按修改范围读对应规范。换项目重新填写，换 AI 工具复用同一份权威内容。

这次整理参考了《BOSS AI规范化编程》的具体文件组织方式：项目入口、目录、编码、前端、UI、数据库、需求、方案和质量检查。原文中的 Go/Kratos/GORM/Vue、某种响应码、特定组件和发布方式属于它的项目实例；新项目仍由自己的代码和配置决定。

## 项目首先得到哪些文件

带前端和数据库的项目可以形成下面的结构。已有规范先沿用真实路径；不适用的类别不创建空壳。

```text
AGENTS.md                         # 或实际工具使用的 CLAUDE.md
docs/
  conventions/
    directory-structure.md        # 文件归属、依赖方向、正反例
    language.md                   # 实际语言的编码规则
    frontend.md                   # 前端工程组织
    ui.md                         # 页面视觉与交互
    database.md                   # 数据与迁移规则
    requirements.md               # 需求怎样写
    technical-design.md           # 技术方案怎样写
    testing.md                    # 测试怎样选、放、运行
  requirements/tasks.md           # 某个功能的具体需求
  designs/tasks.md                # 这个功能的具体方案
```

最后两份只有确实存在功能任务时才建立。`requirements.md` 教需求的写法，`requirements/tasks.md` 写这次功能的答案；方案也是如此。局部小改可以直接沿用 Issue 或对话，不需要为它增加一套记录系统。

多语言项目可以按目录拆语言规范，Go 项目不会顺便收到一份空的 Java 规范。前端工程和 UI 也分开：前者定义页面、组件、路由、状态和请求边界，后者定义视觉来源、页面状态、输入反馈、键盘与验收。

## 入口要能让 AI 找到落点

完整入口包含项目全景、架构铁律、真实技术栈、概要目录树与文件归属、实际命令和条件读取。独立目录规范维护详细归属与正反例；入口保留系统关系和核心边界。

例如本次可运行的教学任务板使用 Python 标准库、SQLite 和原生 JavaScript：

```text
浏览器 → app/http.py → TaskService → SQLiteRepository
app/server.py 负责连接生命周期和依赖组装。

http.py：HTTP/JSON 和状态映射，不写 SQL。
service.py：标题校验与任务规则，不导入 HTTP/SQLite。
storage.py：参数化 SQL 与事务，不决定页面提示。
web/page.mjs：页面状态与 DOM。
web/api.mjs：统一请求和错误转换。
```

目录规范进一步规定：测试放 `tests/test_*.py`，迁移放 `migrations/NNN_*.sql`，具体需求和方案放对应文档目录；生成的 `dist/` 和本机数据库由忽略配置管理。新增领域先确定职责与依赖，同时更新入口概要和详细目录规则。

技术栈需要证据。这个项目的 `pyproject.toml` 声明 Python ≥3.11，CI 声明 Python 3.11，本轮本机运行的是 3.14.7；三者不能混成“已经验证 3.11”。没有框架、npm scripts、格式工具或覆盖率配置，就明确写没有，不能编造一个理想命令。

多服务项目的子入口再补本服务真实构建命令、数据库/ORM/核心表、外部依赖、定时任务和特有约定。任务板只有一个服务，这些信息已在根入口，无需复制出一份服务说明。

## 用一个功能走完开发过程

具体需求是“本机用户可以创建待办并标记完成”。它不包含账户、支付、外部同步或生产部署。

AI 先读入口，再读目录和对应语言规范；这次跨 HTTP、业务、数据库和页面，还需要读数据库、前端、UI、需求、方案与测试规范。只修改一处文案时，读取范围就可以小得多。

需求按影响选粒度：跨模块或涉及数据、接口、权限、金额、兼容的变化写完整说明；单模块行为变化写简化目标、规则与 AC；可逆小修写一句话加验收条件。关键歧义先澄清，不能拿猜测当业务规则。

任务板的验收写成这样：

| 场景 | 可观察结果 |
|---|---|
| 有效标题创建任务 | 返回 201，标题去掉两端空白，列表可见，初始未完成 |
| 空白、非字符串或超过 80 字符 | 返回 400，不新增数据 |
| 完成现有任务后重复调用 | 返回相同任务，done=1，不新增任务 |
| 完成不存在的任务 | 返回 404，其他数据不变 |
| 页面提交失败 | 展示错误，保留输入，恢复按钮 |

“支持完成，功能正常”无法替代这些条件。需求也要区分代码已实现、哪些场景已验证、哪些尚未验证。

跨模块的方案回答八个问题：涉及哪些模块、各处改什么、数据流、接口入出参、失败处理、兼容影响、验证方法、出问题怎样恢复。小改用一段话回答适用问题即可。

在这次方案里，HTTP 解析 JSON，service 校验标题，storage 绑定参数写入，页面根据响应显示结果。非法标题不写入；完成操作将状态赋为 1，重复执行保持同一结果。恢复本机代码与恢复数据库数据是两件事；没有做数据恢复演练，就不能声称两者都已验证。

按目录实现后，运行真实检查。本轮基线 8 项 unittest、两个 JS 模块的语法检查和编译/静态复制通过。浏览器也验证了空列表、创建、完成，以及停止服务后的错误提示、输入保留和按钮恢复。

这些证据各有范围：构建不证明交互，搜索 `except` 不证明所有异常处理正确；自动行为测试也不证明移动端、键盘、读屏和生产环境都正常。未执行的项目继续标明未验证。

## 需求变了，怎样同步旧文件

随后模拟一个新要求：“默认隐藏已完成任务，勾选后显示全部。”

它会改变 GET 列表的默认语义。实现增加 `include_done=0|1`，页面增加复选框；非法或重复参数返回 400。原来“返回全部”的 AC-T4-v1 保留在修订记录中，新版本 T4-v2 描述默认未完成列表，并补显式全部与非法参数验收。不能把兼容影响写成“没有影响”，因为未知外部调用方未验证。

`sync` 读取需求变化、差异、调用方和测试，再更新具体需求与方案。这次实际改了 7 个代码/测试文件和 2 个功能文档；10 项测试、JS 语法和构建通过，浏览器确认默认隐藏、勾选后显示已完成项。

八份通用规范无须跟着重写：目录、架构、技术栈、命令、schema 和写法都没变；新增筛选继续遵守已有 API、页面状态和测试隔离规则。一次业务变化通常修改具体需求、方案和相关接口/测试，需求的“编写规范”只有写法本身变化时才改。

如果变化引入新目录、调整依赖方向或更换构建命令，就要同步入口和对应目录、语言、前端或测试规则。旧决策保留替代关系，计划与现状分别写；代码偏离仍然有效的需求时，应报告实现冲突。

这次完整示例和可重放同步补丁都保存在技能包中。它们证明了本轮文件和本机检查的实际范围，尚不是独立代理行为评估，也没有验证其他 AI 客户端的真实加载。

## 换项目与换工具

在支持命名调用的代理中，可以发出：

```text
$ai-project-conventions init
$ai-project-conventions sync origin/main
$ai-project-conventions audit origin/main
$ai-project-conventions check
$ai-project-conventions add standard directory
```

这是代理操作语义，不是本包提供的终端 CLI。`init` 创建或合并文件，`sync` 回补影响，`audit` 只读找漂移，`check` 提供结构/质量线索，`add` 补明确需要的一份文件。`workflow` / `resume` 仍是可选开发辅助。

核心由 Markdown 入口、参考和模板组成，不依赖特定代理 API。接入多个工具时，其他入口先引用同一权威正文，再按需要补工具增量，避免复制后各自漂移；已有镜像约定才沿用镜像。工具发现、加载和作用域仍需按实际配置核实，复制文件不等于加载验证。

当前包基线是 3.1.0，六类 32 个稳定规则 ID 及正文保留。个人技能更新与业务项目采用分开，本次没有升级真实业务项目的规范。
