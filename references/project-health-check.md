# 项目结构健康度检测

## 使用边界

`check` 是只读的结构审查，不等同于编译、性能压测、安全审计或完整架构评审。脚本只收集可重复的静态证据；模块职责、业务边界、团队协作和长期演进仍需阅读代码、配置、测试、Git 变化及已批准文档后判断。

检测报告必须区分：

- `confirmed`：有代码、配置、测试、运行结果或已批准文档直接支持。
- `needs-confirmation`：存在信号但需要负责人或目标环境确认。
- `not-applicable`：当前项目有证据表明该维度不适用。

## 检测层级

| 层级 | 可依据的原则/规范 | 主要判定问题 | 典型证据 |
|---|---|---|---|
| 类与函数 | SOLID、圈复杂度、认知复杂度 | 职责是否单一，是否难以测试或复用 | 类/函数长度、分支、参数、调用方和测试 |
| 包/模块 | REP、CCP、CRP、ADP、SDP、SAP | 模块边界是否清楚，内聚与耦合是否可控 | 目录职责、导入图、公共入口、变更共现 |
| 依赖方向 | 依赖倒置、稳定依赖原则、抽象与主序列距离 | 依赖是否指向稳定抽象，是否存在环 | import/require/use、依赖图、接口和适配器 |
| 系统划分 | DDD 限界上下文、康威定律 | 模块边界是否与业务边界和团队责任对齐 | 领域词汇、数据所有权、团队/服务边界 |
| 长期演进 | 架构适应度函数（Fitness Function） | 结构是否会随时间腐化，是否有可持续门禁 | CI 检查、架构测试、ADR、指标趋势 |

单文件代码过多是横跨“类与函数”“包/模块”“职责边界”的文件级风险，必须单列专项，不得因为模块平均指标正常而隐藏。

## 一页纸评分表

使用 0/3/5 离散评分，权重合计 100%。加权总分为 `sum(维度得分 / 5 * 权重)`，满分 100；四舍五入到整数。报告同时给出原始分、加权分和证据置信状态。

| 维度 | 权重 | 0 分（病态） | 3 分（及格） | 5 分（优秀） |
|---|---:|---|---|---|
| 依赖方向 | 20% | 存在循环依赖或核心层依赖不稳定细节 | 无环，但偶有倒挂或绕过抽象 | 单向、依赖倒置彻底，边界由检查守护 |
| 模块划分 | 20% | 按技术堆叠，模块边界混乱 | 有业务模块但职责或入口不稳定 | 按限界上下文纵向切分，内聚高且依赖少 |
| 职责边界 | 15% | 大量上帝类/上帝模块或大 `utils` 垃圾桶 | 有共享层但归属和准入可控 | 共享代码有明确归属，模块职责可解释 |
| 变更局部性 | 20% | 一个需求经常改动 6 个以上模块 | 通常改动 3–4 个模块 | 通常只改动 1–2 个模块 |
| 耦合度 | 10% | 高扇入且频繁变更，或跨层细节泄漏 | 耦合尚可控，有少数脆弱连接 | 稳定抽象隔离变化，耦合可观测 |
| 抽象层次 | 5% | 业务逻辑和技术细节混写 | 偶有混层 | 业务、应用、基础设施层次清楚 |
| 测试/构建 | 5% | 测试全靠集成环境或无法独立构建 | 有单测但结构不镜像 | 模块可独立测试/构建，门禁真实有效 |
| 演进健康度 | 5% | 明显腐化且无指标或回补机制 | 基本稳定，偶尔人工清理 | 有适应度函数、趋势指标和定期回补 |

### 单文件规模专项

脚本默认以“去除空行和整行注释后的代码行数”作为规模信号，并同时统计顶层类/函数等符号。阈值是预警，不是跨语言真理；若仓库已有约定，优先采用项目约定并在报告中注明。

| 等级 | 默认信号 | 处理要求 |
|---|---|---|
| 正常 | 代码行数 `< 400` 且顶层符号 `< 20` | 记录抽样结果即可 |
| 预警 | 代码行数 `>= 400` 或顶层符号 `>= 20` | 标出文件职责、变更频率和建议拆分点 |
| 严重 | 代码行数 `>= 800` 或顶层符号 `>= 40`，或一个文件同时承担 3 类以上职责 | 必须给出 P0/P1 改进建议；“职责边界”不得评为 5 分 |

专项也可用同一尺度呈现：正常为 5 分、预警为 3 分、严重为 0 分。专项不新增基础权重，但严重信号必须降低“职责边界”或“模块划分”的判断，并在总评中标记风险；不得用其他维度的高分抵消未处理的大文件。

以下目录默认排除：`.git`、依赖目录、构建产物、缓存、供应商目录和生成目录。测试文件单独统计，不因测试集中而误判生产模块；若测试文件本身难以维护，仍应报告。

## dead code 专项

dead code 检测只产生候选，不直接修改或删除代码。默认覆盖三类信号：

| 候选类型 | 检测信号 | 默认置信度 | 处理方式 |
|---|---|---|---|
| 内部符号 | 函数、类、类型或箭头函数的定义名称在代码中没有其他引用 | 高；测试文件或动态语言降为中 | 检查反射、依赖注入、插件注册、外部调用方后再删除 |
| 未使用导入 | Python 导入名称在导入行之外没有代码引用 | 中 | 先确认副作用导入、类型检查和条件导入，再清理 |
| 孤立模块 | 非入口、非测试源码文件没有其他源码的入站文本引用 | 低 | 检查动态导入、路由扫描、构建入口、脚本调用和运行时加载 |

报告至少包含文件、行号（适用时）、符号/模块名、候选类型、置信度、检测原因和人工确认项。反射、字符串路由、动态导入、代码生成、宏、框架生命周期方法、CLI 入口和仓库外消费者会造成漏报或误报；启发式结果不能作为自动删除依据。

如果项目已经配置真实的 dead code 工具（例如语言生态的未使用导入、未引用导出或依赖分析检查），先确认命令存在再运行，并把工具版本、命令和结果作为 confirmed 证据；不得因为工具未安装就宣称检查通过。dead code 候选会影响“职责边界”“测试/构建”和“演进健康度”判断，但不单独增加基础评分权重。

## 代码质量专项

先读取项目清单、脚本、CI 和工具配置，优先使用仓库已经采用的检查命令。通用脚本补充下表中的跨语言启发式信号：

| 类别 | 通用信号 | 更高置信证据 | 主要影响维度 |
|---|---|---|---|
| dead code | 未引用内部符号、未使用导入、孤立模块 | 项目 dead code 工具、编译器或语言服务器结果 | 职责边界、演进健康度 |
| 代码风格 | 尾随空格、Tab 缩进、超长行 | 项目格式化器/代码检查器及 CI | 测试/构建、演进健康度 |
| 缺陷与潜在 Bug | 裸异常、可变默认参数、宽松等值、空 catch | 类型检查、静态分析、目标测试和代码阅读 | 测试/构建、变更局部性 |
| 安全漏洞 | 硬编码凭证、动态执行、shell 执行、SQL 拼接 | 专项 SAST/依赖扫描、数据流分析和安全审查 | 职责边界、测试/构建 |
| 复杂度与可维护性 | 长函数、分支过多、大文件和符号过多 | 项目复杂度工具、热点变更记录和人工评审 | 职责边界、变更局部性 |
| 重复代码 | 跨文件连续代码块指纹相同 | 项目重复度工具及语义审查 | 耦合度、演进健康度 |
| 测试覆盖 | 测试文件、覆盖率配置和产物是否存在 | 实际覆盖率命令、分支覆盖报告和关键路径测试 | 测试/构建 |
| 代码坏味道 | 大 utils、参数过多、嵌套三元、未完成标记 | 项目检查器、调用方和职责评审 | 模块划分、抽象层次 |

安全和缺陷信号是待确认候选，不得仅凭正则匹配宣称存在可利用漏洞或确定 Bug。覆盖率只有实际产物或真实命令结果才能给出百分比；只发现测试目录或配置时报告“有覆盖率机制线索”，未发现时报告“未验证”。重复代码候选在删除或抽取前必须确认其业务变化节奏相同，避免为了 DRY 制造错误耦合。

## 检查步骤

1. 确定仓库根目录、语言、构建入口、测试入口和比较基线；没有 Git 或基线时说明覆盖限制。
2. 运行 `scripts/check_project_health.py <repo> --format json`，保存文件热点、dead code、代码质量候选和启发式限制。
3. 阅读热点文件、其调用方、导入边界、测试和最近变更；必要时绘制简化依赖图。
4. 对八个加权维度逐项给出 0/3/5、证据位置、置信状态和一句判断；无法证明时写“待确认”。
5. 单独给出文件规模专项分级，列出最多 10 个热点文件及拆分建议，避免只给抽象评价。
6. 单独给出 dead code 候选，按置信度排序；将高置信候选转为人工确认任务，不把候选直接写成“已删除”。
7. 汇总代码质量八类专项；每类区分项目工具结果、通用启发式候选和未验证项。
8. 计算加权总分，列出 3–5 条改进建议；每条建议包含优先级、目标、涉及文件/模块、验证方式和完成信号。
9. 只报告实际执行的命令；未运行的构建、测试、运行环境检查和架构工具单列。

## 固定报告结构

```text
# 项目结构健康度检测
基线：<工作区/提交引用>；范围：<代码、配置、测试、文档和未验证项>

| 维度 | 权重 | 得分（0/3/5） | 加权分 | 置信状态 | 证据 | 判断 |
| ... | ... | ... | ... | confirmed/needs-confirmation/not-applicable | ... | ... |

加权总分：<0-100>/100
单文件规模专项：<5/3/0>；严重热点：<文件列表或“无”>
dead code 专项：<候选数量>；高置信候选：<文件:行号或“无”>
代码质量专项：<风格/缺陷/安全/复杂度/重复/覆盖率/坏味道的状态与数量>
最高优先级改进：<P0/P1 动作>
未验证：<命令、目标环境或需要人工确认的内容>
```

## 改进建议模板

```text
[P0/P1/P2] 目标：把 <热点文件/边界> 的 <问题> 降到 <可观察阈值>
证据：<文件:行号、依赖、变更统计或命令输出>
动作：<拆分/提取端口与适配器/移动归属/补架构门禁>
验证：<真实命令、测试或人工评审>
完成信号：<文件规模、依赖方向、变更范围或指标达到什么状态>
```

建议按“先解除循环/安全边界和严重大文件，再减少职责混合，最后补适应度函数”的顺序排序；不要为了降低行数制造无语义的碎片模块。
