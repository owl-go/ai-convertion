# 项目开发协作流程

具体实现、修复、设计或评审任务，以及 `workflow`/`workflow resume` 时读取本文件。初始化规范和只读审计仍走原命令；本流程不替代六类规则、不实现新的代理运行时，也不要求每个任务经过全部阶段。

## 意图、职责与裁剪

先从用户当前任务和已有授权确定目标与范围。咨询/设计/评审只调查与给出相应结果，用户要求保存方案时才按范围写文档；实现/修复执行已授权工作区修改并验证。任务中已有提交、推送或目标环境授权继续有效；普通开发指令不自动授权发布、生产迁移、群发或外部写入。

| 协作方 | 主要职责 |
|---|---|
| 人 | 目标、优先级、业务含义与重要取舍；提供不可推断的意图或必要授权 |
| AI | 调查事实、提出方案、按授权实现、选择和执行验证、处理反馈、同步与交接 |
| 自动工具 | 已配置的可确定检查与可复核结果；不替人决定业务，不替环境提供未运行证据 |

局部、低风险、可逆变更可合并需求/方案/任务记录，并直接检查相关行为。跨模块、接口、数据迁移、权限或重大取舍按影响深化方案和专项验证。已满足阶段引用已有证据，不重复造文档或重跑无关全量检查。仅对真正不可推断且会改变业务或授权边界的事项提必要问题，其他独立工作继续；阶段表不是逐步审批流。

## 最小任务记录

每项任务可追踪：目标、范围/非目标、适用依据、验收条件、验证方法、当前进度、未决项。可用现有 Issue、任务记录或短任务完成报告；长任务使用 [任务与证据模板](../assets/templates/task-evidence.md) 保存可恢复状态。产物列表示信息需要被记录，不要求独立文件。

开始时标出当前阶段、已经满足的退出条件和下一步。每条待决项说明影响与依赖范围；每条 AC 关联实现或分析位置、验证方法和实际结果。保留计划、已实现、已验证的区别，需求/决策的批准状态独立于实现与验证状态。

## 阶段判断与反馈

### 1. 明确需求

- **输入**：用户任务、已有需求/规则、已确认业务决定。
- **动作**：明确目标、范围/非目标、正常和异常行为、适用非功能约束；写可观察验收，区分事实、假设与影响实现的待决问题。
- **产物与退出条件**：每项拟实施行为有可判断的完成条件；关键待决问题及依赖范围可见。咨询任务可在问题得到有依据的回答后结束。
- **失败后的下一步**：范围或业务含义冲突回到责任人决定；只阻塞依赖部分，不能用实现默认值替代业务决定。

按需读 [需求规则](requirements.md)；小任务在同一记录保留上述信息即可。

### 2. 检查现状与影响

- **输入**：任务边界、项目实际入口、批准规格/ADR、代码/配置/测试与工作区状态。
- **动作**：阅读相关行为与调用方，识别模块、接口、数据库、UI、测试、运维和文档影响；定位真实检查命令与环境。当前事实以实现证据确认，期望行为以批准要求确认。
- **产物与退出条件**：受影响边界有证据位置，候选影响、需求/现状冲突与未覆盖范围可定位；有足够依据选择下一步，不将文件名线索冒充结论。
- **失败后的下一步**：扩大到相关调用方或配置补证；无法确认的业务/权限含义保留待决，代码与批准需求冲突不静默改写需求。

复杂变化使用 [影响图与账本](../assets/templates/document-impact-map.md)，沿入口的六类条件路由读取适用规范；无影响的类别给出依据，不补空文档。

### 3. 形成方案与任务

- **输入**：验收、已确认影响、约束、风险与适用规则。
- **动作**：按复杂度选择设计深度；明确边界、契约、兼容、失败处理和验证；拆成可验证小步，标依赖与退出条件。长期重大取舍按项目约定记录 ADR。
- **产物与退出条件**：各小步能关联 AC/规则、实现范围和验证方法；影响业务或重要取舍的待决项已处理，或依赖范围明确保持待完成。设计/方案任务到其有依据的结论与限制即可完成。
- **失败后的下一步**：边界或可验证性不足返回调查/需求；未批准提案保持计划状态。不能把“方案完成”当作实现已获授权。

使用已有设计载体，按需取 [技术方案](../assets/templates/technical-design.md)、[ADR](../assets/templates/adr.md)，无需为每个小改动建 ADR。

### 4. 实现与即时反馈

- **输入**：已授权实施范围、适用方案/任务、工作区现状与规则。
- **动作**：按小步实现，运行能产生相关反馈的检查并修正；保留任务外改动。需求、架构、接口、数据或 UI 变化在本任务内沿影响映射同步权威文档与关联链接。
- **产物与退出条件**：拟交付行为在明确版本中已实现，相关即时检查有结果，文档影响逐项已更新/不适用/待确认；遗留项与残余范围可见。完成该阶段不代表全部验收已验证。
- **失败后的下一步**：定位实现、测试、环境或方案问题，修复后重跑受影响检查；发现新的业务冲突返回需求/方案，不扩范围掩盖问题。

文档同步遵循 [维护流程](maintenance-workflow.md)，沿用已批准决策，保留旧 ADR 和验收修订。

### 5. 验证

- **输入**：实现版本、AC/规则映射、项目门禁与目标环境范围。
- **动作**：按风险选择测试、构建、契约、交互、迁移/恢复、性能等适用验证；运行真实命令/人工步骤，记录环境和结果。低成本有效检查起步，有新影响、失败或残余风险才扩大/重复。
- **产物与退出条件**：每项验收有实际证据或明确未验证结论；通过、失败、未验证分开。适用 MUST 门禁未满足时保持交付待完成，或关联已批准且仍有效的例外。只有满足实际完成条件才可称实施任务完成。
- **失败后的下一步**：产品缺陷回实现，验收冲突回需求/方案，环境缺失保留未验证及所需条件。静态检查不能冒充交互，局部通过不能外推生产验证；重试保留首次失败并有停止条件。

选择依据是 [测试规则](testing.md)，项目映射可使用 [质量门禁模板](../assets/templates/quality-gates.md)；缺少工具写事实与替代验证，不虚构命令或阈值。

### 6. 评审与交付

- **输入**：需求/决策、实现差异、检查结果、文档账本与剩余风险。
- **动作**：对照范围与验收检查差异、边界、兼容和维护成本；按项目已有审查流程处理反馈。评审请求仅给出有证据的发现与结论，不自动修复；已授权实施任务则处理其范围内反馈并复验。
- **产物与退出条件**：评审范围和结论明确，反馈有处置；交付说明改动、实际验证、遗留项、未决问题、适用恢复措施与文档状态。咨询/评审完成与功能/发布完成分别判断。
- **失败后的下一步**：实现反馈回实现并重验，需求/决策冲突回相关阶段；必须检查未过保持未完成，不因报告写完而标成功。

### 7. 发布与观察（按授权适用）

- **输入**：明确的目标环境操作授权、项目既有发布流程、已满足门禁、观察与恢复条件。
- **动作**：仅按实际任务处理发布、迁移或其他目标环境操作，检查约定指标/日志和异常恢复；开发交付可在此阶段不适用时结束。
- **产物与退出条件**：授权操作的实际状态、观察结果与目标环境范围有证据；只称已验证的范围。缺少授权时标“不在本次范围”，不将业务发布当作默认下一步。
- **失败后的下一步**：依停止条件中止后续动作，按已授权恢复方案处理并验证；需要新的不可逆动作或目标时遵守实际授权边界。

按需使用项目实际 [运维/恢复手册](../assets/templates/operations-runbook.md)，未知环境、命令、指标和恢复能力保持待确认/未验证。

### 8. 反馈与维护

- **输入**：重复缺陷/失败、漂移、交付/观察证据与现行规则。
- **动作**：定位缺口属于测试、工具、规则还是文档，选择最小有效改进；保留原因与原失败场景，确认改进能发现/预防对应问题。一次偶发失败不自动成为全项目永久规则。
- **产物与退出条件**：反馈有处置或跟踪；落地改进有验证与适用范围，未完成项明确。没有值得长期固化的发现，可说明依据，不要求增加文件。
- **失败后的下一步**：改进未产生有效反馈时复查原因与适用性；环境或阶段不能验证的项目记录限制，不能以“加了规则”宣称已解决。

项目业务变化与通用基线升级分开；维护/升级依据 [Harness](harness.md) 和维护流程，本次开发流程扩充不改变 `2.0.0` 六类规则契约。

## 中断与恢复

中断前在现有任务载体保存：已验证事实及版本/环境、工作区与未提交差异、关键决策与授权范围、已完成/进行中/受阻项、原始失败和恢复点、剩余验收、待决项和下一步。长操作或外部状态只记录可复核信息，秘密与敏感测试数据不进入账本。

`workflow resume [task-record]` 先读取记录，再核实实际仓库/分支/版本、工作区、相关配置与长操作/环境状态；记录是线索，不保证现实仍相同。没有变化的已完成工作直接复用证据，改变的部分重新判定影响；检查无须无条件全量重跑。确认当前阶段和下一步后继续，原授权未变则沿用，目标或业务决定变化才澄清依赖选择。

省略记录时使用上下文已知任务载体；多个任务无法识别时问目标，缺少旧记录时从已知证据重建并说明恢复盲区。禁止凭“恢复”去重复已经完成的迁移、发布或其他有状态动作；先核实状态与是否仍授权。

## 调用与教学示例

以下是向支持此语法的代理发送的对话指令，核心流程不依赖 `$` 前缀、固定客户端或专有 API：

```text
$ai-project-conventions workflow 实现订单取消原因，先核实批准需求与兼容约束，再按影响实现和验证。
$ai-project-conventions workflow 只读评审取消原因方案的边界、迁移与验收缺口。
$ai-project-conventions workflow resume docs/tasks/order-cancellation.md
```

`docs/tasks/order-cancellation.md` 只是任务记录路径示例，执行时使用项目真实载体。也可自然表达“按本 skill 开发流程设计/实现/评审某任务”；没有具体任务的纯技能调用仍保持原 `init`/`sync` 默认。

**教学场景：取消订单增加原因。** 先把“原因必填、老客户端兼容、退款是否在范围内”等标为事实或待决，确定 AC；调查取消/发货状态、接口、模型、页面和已有测试。方案按批准结果拆成契约/数据兼容、状态/校验、UI、验证与文档同步小步，每步记录预期证据。

| 小步 | 适用依据与证据 | 失败/未决后的下一步 |
|---|---|---|
| 需求/现状/方案 | `REQ-001`～`REQ-005`、`ARC-001`/`ARC-002`/`ARC-004`；AC、调用方与兼容选择 | 原因是否必填未决定时保留依赖范围；评审任务在结论结束，不实施 |
| 数据/接口/状态实现 | `DB-001`/`DB-003`/`DB-005`/`DB-006`、`COD-002`/`COD-003`/`COD-004`；旧数据语义、并发/幂等与日志保护 | 需求必填而代码可选时报告差异；迁移恢复未验证保持未验证 |
| UI 与验证 | `UI-001`～`UI-005`、`TST-001`～`TST-005`；表单/反馈、目标视口、键盘/交互与错误/回归结果 | 截图不能代替交互，缺目标环境补条件而非宣称通过 |
| 文档/评审/交接 | AC→实现/验证，影响账本与当前/计划状态，遗留与恢复点 | 无模块取舍变化可判 ADR 不适用；发布不在授权范围时交付开发结果 |

示例不代表任何真实订单项目已实施或验证。首次执行记录实际证据；恢复时核对记录与当前状态。按需求/架构/接口/数据/UI 影响在同一任务用 `sync` 的维护方法更新相关权威来源与链接，无需另行重复全部规范初始化。
