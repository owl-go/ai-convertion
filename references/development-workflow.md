# 可选开发协作辅助

`workflow <具体需求>` 和明确要求按本 skill 实现/修复任务时读本文件。已有项目规范就复用，日常任务不重新 `init`。这里规定代理接到需求后做什么，不要求用户学习阶段名称或填写全套文档。

## 选择本辅助时做这五件事

1. **读现场。** 读取项目实际入口、相关需求与规则、实现文件、调用方、已有测试；检查工作区改动。从配置、README 或 CI 确认真实检查命令和运行目录。先圈定相关范围，保留任务外内容。
2. **写验收和改动清单。** 把需求写成“给定输入/状态，操作后应看到什么”，列实际拟改路径及原因。用现有 Issue 或一条短记录保存目标、验收、影响、验证方法、进度与未决项；无需几十个规则 ID 或多份空文档。用户明确的新要求作为需求修订依据，保留旧行为及变更说明，不因旧文档不同永久等待确认。
3. **做最小相关修改。** 沿用现有模块和接口，改相关实现，补或调整能检出目标行为的测试。实现请求持续推进到结果；咨询/方案/评审则给出相应结论，不自动实施。只有不可推断且影响业务或授权范围的选择才提必要问题，其余独立工作继续；无需逐步等待批准。
4. **跑检查，处理失败。** 执行针对验收与受影响行为的真实检查，包含相关旧测试。失败先定位：实现缺陷就修复；旧断言与明确的新要求冲突则按修订调整并保留理由；工具/环境缺失标未验证。修复后重跑相关范围，保留原失败。静态检查不证明交互，局部测试不证明生产；只有新增影响、失败或残余风险才扩展/重复验证。
5. **同步说明，给具体结果。** 更新本次实际受影响的需求、架构、模型/迁移或 UI 说明与链接；未影响的文档说明依据。交付实际修改路径、行为、命令/检查结果、文档更新及未完成范围。验收或必须门禁未满足时保持待完成，或关联已批准且有效的例外，不能把报告写完当成功。

每步的完成判断直接看产物：已找到相关代码和命令；验收与拟改路径清楚；相关实现已改；检查有真实结果；说明和交付反映实际状态。失败返回查因与修复，不增加一层填表流程。短任务可在完成报告中表达同样信息，长任务保存 [短任务记录](../assets/templates/task-evidence.md)。

## 遇到不同任务，先做什么

| 任务 | 具体起手动作 | 完成时核对 |
|---|---|---|
| 功能 | 读入口、实现和调用方，把正常/异常行为写成用例 | 目标用例和相关旧行为通过，实际改动范围明确 |
| 缺陷 | 用现有用例或最小输入复现，记原失败，再定位实现 | 修复后相同场景通过，相关回归通过；不能复现时说明限制 |
| UI | 找现有组件/token、目标状态、视口与操作流程 | 实际状态/尺寸、键盘或交互结果及适用视觉证据；无浏览器/渲染环境报未验证 |
| 数据 | 读 schema、调用方、旧数据语义和迁移工具 | 约束/并发、兼容组合、升级和适用恢复有证据；应用回退不等于数据恢复 |
| 纯文档 | 对照现行代码/配置/批准决定和实际引用 | 更新路径、事实来源、链接结果清楚，不因文档任务改业务代码 |

只用项目实际工具，未知命令、版本、阈值与目标环境标待确认。六类规则按入口触发读取，保持 [架构](architecture.md)、[代码](code.md)、[数据库](database.md)、[需求](requirements.md)、[测试](testing.md)、[UI](ui.md) 的原要求；不涉及的数据库/UI 无需造文档。

## 什么时候多做一些

跨模块、公共接口、数据库迁移、权限或重大取舍变化时，先按实际风险补齐边界、兼容、错误/取消/清理、验证与恢复说明，再拆成可验证小步。小且可逆变更在短记录内解释即可；复杂取舍按项目约定使用 [技术方案](../assets/templates/technical-design.md)、[ADR](../assets/templates/adr.md)、[迁移计划](../assets/templates/migration-plan.md) 或 [质量门禁](../assets/templates/quality-gates.md)，不要求全部创建。

人在不可推断的目标、优先级、业务和重要取舍上决定；代理调查、实现、验证并处理反馈；工具提供已运行的可确定结果。已有授权持续有效，提交/推送/目标环境操作沿实际任务范围执行。普通功能开发不自动授权发布、生产迁移或外部写入；发布适用时沿项目现有流程记录目标环境、观察与异常恢复。

重复失败需要时改测试、工具、规则或文档，重新验证改进能发现对应问题；一次失败不自动增加永久通用规则。本流程不改变六类稳定规则 ID 的含义，项目业务变化与通用版本升级分开。

## 文档怎样跟着改

在同一任务沿 [sync 的维护方法](maintenance-workflow.md) 先列实际受影响文档，再更新权威来源与相关链接。明确新用户要求可以修订旧需求；若只是代码偏离仍有效的批准要求，则报告差异，不按代码静默改写业务。意图不清的部分保留待决。

当前与计划分开，已实现与已验证分开；旧 ADR 保留并指向替代决定，旧验收留下修订及原证据。每项文档影响给出已更新/不适用/待确认结论。无法同批完成的事项写剩余范围与下一步。同步不要求另外重新初始化项目，也不会自动监听每次代码修改。

## 中断后继续

`workflow resume [task-record]` 先读记录，再核实仓库/分支/版本、工作区差异、现行需求和已有检查结果。有效的已完成工作直接复用，只重做发生变化或尚未验证的部分。记录只需补充已验证事实、决策/授权、长操作状态、剩余项和下一步；敏感数据不进入记录。

省略路径时使用上下文已知任务；多条记录无法识别时问目标，缺旧记录则重建并说明盲区。有状态操作先核实是否已经完成及是否仍授权，不能因为“恢复”重复迁移或发布。

## 用户怎样调用

以下是代理对话操作，不是独立 CLI；`$` 是支持此写法客户端的示例，其他工具可按真实配置或自然语言表达同样意图：

```text
$ai-project-conventions workflow 订单取消必须填写去除首尾空格后非空的原因，保存原因；空原因和已发货订单拒绝且不改变订单。
$ai-project-conventions workflow 只读评审这个取消原因方案。
$ai-project-conventions workflow resume docs/tasks/order-cancellation.md
```

示例路径要换成真实记录。只有 `workflow` 且上下文没有任务时澄清目标，不转成初始化。仅调用 skill 而未请求具体任务时，保持原 `init`/`sync` 默认。
