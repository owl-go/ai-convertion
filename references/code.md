# 代码规范

适用于代码组织、错误处理、输入边界、资源、日志与依赖引入。沿用项目语言习惯和格式化配置；通用基线回答行为与边界，技术栈补充回答具体 API 和工具。

| ID | 等级 | 范围 | 要求 | 理由 | 验证方式 | 失败处理 | 例外条件 |
|---|---|---|---|---|---|---|---|
| COD-001 | SHOULD | 命名与组织 | 命名对应领域术语；模块内聚，公共入口清楚；格式与导入服从项目配置 | 使职责与变更影响可识别 | 术语/职责审查及已有 formatter/linter 的检查模式 | 修复歧义/违规，结构候选先确认 | 外部协议命名或迁移期别名记录映射 |
| COD-002 | MUST | 不可信输入与错误 | 在信任边界做类型/范围/权限校验；区分预期业务错误与系统失败，保留因果与可用错误反馈 | 防止非法状态与静默失败 | 边界/错误路径测试，检查校验位置与错误传播 | 正确性或权限缺陷阻断 | 校验可由已验证上游边界承担；注明信任依据 |
| COD-003 | MUST | 文件/连接/锁/临时资源 | 成功、异常、超时、取消均按所有权释放；长操作遵守项目超时和取消语义 | 防止泄漏、悬挂与重复副作用 | 失败注入/取消验证，检查语言资源管理结构 | 泄漏或不安全重试阻断 | 平台托管资源须有生命周期证据 |
| COD-004 | MUST | 日志与诊断 | 关键失败带可关联上下文；凭证不入代码/日志/证据，敏感字段按项目策略最小化或脱敏 | 使失败可定位而不泄露数据 | 日志样本、敏感路径测试/扫描与人工审查 | 泄密阻断并按项目事件流程处理 | 凭证泄露禁止例外；敏感字段按明确批准策略处理 |
| COD-005 | SHOULD | 新依赖 | 说明用途、已有替代、维护/许可/安全及运行成本；遵守现有版本锁定策略 | 减少长期供应链与维护负担 | 清单/锁文件差异、引入理由、已有扫描工具 | 不明来源或未解决风险先澄清 | 有限定范围与替换条件的试验依赖可记录例外 |
| COD-006 | MUST | 可观察行为变化 | 将行为与边界映射到相称验证；缺陷修复有回归证据 | 让改动可判定完成 | 按 [测试规范](testing.md) 选择范围与证据 | 必须验收未验证保持待完成 | 自动回归不适用时说明原因与有效替代验证 |

## 技术栈落地

用 [技术栈补充模板](../assets/templates/stack-profile.md) 记录实际语言/运行时及来源、formatter/linter/类型/依赖工具、工作目录、环境与检查模式；命令发现后实际运行才能写“已验证”。框架错误处理、事务、资源生命周期等具体方式指向配置/代码例。缺少工具写“未配置/待确认”及人工替代，不自行规定全栈一致框架或阈值。

规范正文用 [规则模板](../assets/templates/standard.md)，测试与质量工具映射用 [质量门禁](../assets/templates/quality-gates.md)。检查：名称能解释职责；校验与错误路径可定位；清理覆盖失败；日志不含敏感信息；依赖有用途和证据；检查候选与已确认缺陷区分。文件长度/dead code 等健康脚本输出是启发式，只有项目采纳才成为门禁。
