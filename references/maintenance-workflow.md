# 持续审计与回补

回补的目标是恢复“事实、决策、规范、检查”之间的一致性，不是把所有代码变化翻译成文档。

## 触发源

- 架构边界、技术栈、依赖、构建命令或目录职责变化。
- 公共 API、事件、协议、数据库结构或权限模型变化。
- CI/CD、部署、回滚、目标环境或运行责任变化。
- 重复缺陷、事故复盘、安全发现或相同例外反复出现。
- 需求/设计/ADR 获批、被替代或失效。
- UI 设计系统、交互状态、目标视口或可访问性约定变化。
- 项目主动采用新的通用基线版本；这是规范升级，不同于项目需求/架构变化，不将项目局部取舍推广到全部项目。
- 到达 `review-cycle`，或文档中的路径、命令、版本、负责人无法验证。

## 回补步骤

1. **选择比较范围**
   - 用户指定基线时使用该基线。
   - 没有基线时，检查工作区与当前分支的可用差异，并明确此次审计不能证明更早的历史无漂移。
   - 可运行 `collect_project_evidence.py <repo> --since <ref>` 获取变化线索。
   - 脚本 `--since` 的已提交比较为 `<ref>...HEAD`（merge-base），并合并暂存、未暂存与未跟踪路径；报告同时记录用户指定 ref 和实际比较语义。
   - 读取用户提供的需求/架构决策变更、已有规格系统或文档差异；它们可能尚无代码变化，不能只靠 Git 文件名发现。

2. **读取变化本身**
   - 阅读差异、调用方、测试和相关配置，不仅依赖文件名分类。
   - 对每项候选影响记录证据位置与置信状态：`confirmed`、`needs-confirmation`、`not-applicable`。
   - 复杂变化先形成具体文档影响清单，使用下方映射；确需长期维护才使用 [影响图模板](../assets/templates/document-impact-map.md)。简单变化可在交付回复或已有需求内表达；只纳入实际受影响的文档。

3. **判定权威方**
   - 用户明确提出并授权的新需求是修订依据：保留旧行为与新要求，更新相应验收和依赖产物，不因旧文档不同永久等待确认。仍不清楚或影响授权范围的选择单列待决。
   - 已批准 ADR/规格仍有效而实现偏离：优先标记实现问题，不用改文档掩盖偏离。
   - 实现与验证证据代表已批准现状，而说明文件陈旧：更新文档。
   - 重大行为已落地但没有决策记录：补写“事后 ADR”，明确其为回补记录并给出证据日期。
   - 无法判断产品、权限或生产意图：保留冲突并请求责任人确认。

4. **沿影响图更新**
   - `audit` 保持只读，输出影响清单与建议；`sync` 只处理已授权范围。先改权威文档，再修正实际工具入口路由、索引和下游链接，入口同步遵守 [工具适配](tool-adapters.md)。
   - 当前架构/需求按授权更新；新决策通过 `supersedes` 指向旧 ADR，旧 ADR 标 `superseded` 并链接替代记录，保留原决策正文。变更验收用修订记录关联旧/新 AC ID，不抹去历史。
   - 需求/规则/契约使用稳定 ID；每个受影响 AC 链接实现位置、测试/人工验证及结果。区分计划、已实现、已验证，计划方案不写入“当前架构”冒充现状。
   - 检查规则对应的脚本、测试、CI 或人工门禁是否仍真实存在。
   - 删除重复缓存；历史决策用 `superseded` 链接保留，不改写成从未发生。

5. **验证闭环**
   - 验证受影响的命令、路径、链接、术语、规则 ID、文档状态和复查日期。
   - 对照本次影响清单确保每一项已更新、明确不适用或进入待确认队列。
   - 最终报告标明比较基线、覆盖范围和无法证明的区域。
   - 对照需求、接口/schema、模型、迁移、测试与 UI 的实际相关性验证一致；引用与命令验证仅限实际执行范围。文档与代码在同一变更中交付，跨仓库或环境未完成项明确跟踪责任/下一步。
   - 报告实际更新的文件、每项已更新/不适用/待确认结论及未验证证据；代码偏离已批准业务要求的冲突保持可见。

## 默认文件同步映射

沿用项目实际权威路径；以下为新项目默认路径。影响清单可以在回复里给出，不默认创建文件。

| 变化 | 首先更新 | 相关核对 |
|---|---|---|
| 模块/依赖/系统关系/目录归属 | 入口全景、架构铁律、目录树与归属表 | 真实源码路径、依赖、相关设计/ADR；新文件有归属 |
| 栈/版本/启动/检查命令 | 入口技术栈与运行检查 | 清单/锁文件/CI；受影响语言/前端/测试规则 |
| 语言/config/错误/资源/并发 | `docs/conventions/language.md` | 实际配置与例子；语言版本同步入口 |
| 前端组织/状态/API/构建 | `docs/conventions/frontend.md` | 入口目录、配置、UI 状态与相关设计 |
| token/组件/页面状态/交互 | `docs/conventions/ui.md` 或具体 UI 规格 | 组件/样式来源、需求与视觉证据 |
| 数据规则/模型/事务/迁移 | database 规范或具体模型/迁移文件 | schema、旧数据/应用兼容、需求、设计、测试 |
| 业务规则/AC | 具体需求及 AC 修订；写作约定变化才改 requirements 规范 | 实现、测试、设计/UI/数据的实际影响 |
| 实现方案/长期决策 | 具体 design / ADR；写法变化才改 technical-design 规范 | 当前与计划、入口架构、依赖/契约与恢复 |
| 回归/检查/隔离/测试路径 | testing 规范及实际测试/结果 | AC 映射，入口命令与配置来源 |

先更新权威内容再修入口条件链接。旧 ADR 保留正文与替代链，旧/新 AC 关联修订；明确用户新要求是合法修订，仍有效要求与实现冲突不能藏掉。需求或方案未落地时明确计划，测试未执行时明确未验证。

## 抗膨胀检查

每次回补同时查找：

- 已能从配置低成本读取、却被多个文档重复缓存的事实。
- 没有真实验证方式或从未影响决策的规则。
- 已失效的路径、命令、版本、人员姓名和临时例外。
- 两个 ID 不同但意义相同的规则。
- 已替代文档仍被活动路由引用。

删除内容时保留必要的历史决策链和迁移影响；只清理失效的活动规范与重复副本。
