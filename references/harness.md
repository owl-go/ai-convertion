# Harness 采用与反馈闭环

本包通用基线版本：`3.0.0`。这是规则契约版本，不是技术栈版本或一次 Git 发布。六类规则正文分别在 [架构](architecture.md)、[代码](code.md)、[数据库](database.md)、[需求](requirements.md)、[测试](testing.md)、[UI](ui.md)。首次采用或升级时阅读本文件；日常变更只读触发的类别。

## 三层规则与项目采用

| 层 | 内容 | 权威来源 |
|---|---|---|
| 通用基线 | 跨栈边界、必须回答的问题、检查意图 | 本包带稳定 ID 的规则；项目具体规范保存适用规则与来源 |
| 技术栈补充 | 实际语言/框架/存储的实现方式、配置、命令与环境 | 项目配置/清单/CI，补充说明指向这些事实 |
| 项目约定 | 业务不变量、模块契约、风险容忍、职责与例外 | 已批准项目标准/需求/ADR |

项目采用时在入口简记基线版本、来源与适用性，具体规则按 [文件契约](document-system.md) 写入项目规范。独立 [采用记录](../assets/templates/harness-adoption.md) 仅在明确需要审计升级时使用。将适用基线保存到项目规范目录，使项目不依赖个人 skill 安装路径或其未来更新。可保留一份规则文件或按类拆分；路由始终指向项目内的权威规则。实际架构、模型、需求、测试计划与 UI 规格放在独立产物或已有系统中，以链接关联规则。

通用 MUST 的适用范围先于实现方式；技术栈和项目层将其具体化。更具体层若降低要求，记录显式例外而不是静默覆盖。已有人工规则与基线冲突时保留证据与差异，依照已批准决策处理；无法推断的业务/权限/生产含义才请求决策。在入口路由简述类别适用性与依据；尚未存在的数据库或 UI 不创建空壳，将未来引入写为复审触发。

关键规则使用 [规则模板](../assets/templates/standard.md) 的八项字段。`MUST`（必须）违反时按规则失败处理；`SHOULD`（建议）偏离须说明影响；`MAY`（可选）不作为门禁失败。基线表中的验证是意图，技术栈补充必须将它绑定到已发现的工具或明确的人工检查。缺失工具记为待确认，不伪造命令。例外记录理由、风险、补偿、批准依据、失效条件和跟踪项；禁止例外的规则失败直接阻断。

## 从规则到交付

具体任务或恢复工作读取 [开发协作流程](development-workflow.md)：读现场、写验收/拟改路径、实施、检查与修正、同步说明并交付具体结果。短任务一条记录即可；跨模块、接口、数据或权限等变化按影响补方案与专项验证。咨询/评审不自动实施，规范建立与审计仍走原命令。

确需独立检查映射时使用 [质量门禁模板](../assets/templates/quality-gates.md)，确需交接记录时使用 [任务与证据模板](../assets/templates/task-evidence.md)。[维护流程](maintenance-workflow.md) 定义权威来源与文档同步。流程是协作方式，六类规则契约版本仍是 `3.0.0`，不会因新增 `workflow` 操作自动升级项目采用版本。

## 版本升级

项目不会因个人 skill 更新自动升级基线。`sync`/`audit` 比较采用快照与当前包版本，输出新增、变更、移除规则 ID；同版本正文不同视为漂移。`3.0.0` 相比 `2.0.0` 改变默认文件生成契约：完整入口与少量具体规则替代地图/门禁/采用记录默认集合，workflow/resume 改为可选辅助；六类稳定 ID 与 init/sync/audit/check/add 保留。项目升级应比较入口/模板边界及实际规则，不自动覆盖人工约定。

确需独立升级记录时，差异表记录旧/新版本、规则 ID、要求差异、影响模块与门禁、例外处置、迁移步骤及验证结果。文案澄清可提高补丁号；兼容新增提高次版本；既有要求或 ID 含义的不兼容变化提高主版本。规则 ID 保持含义稳定，删除/替代保留映射。只有完成项目批准的采用与必要验证后才更新采用版本；未知历史按“未记录版本”比较实际文本，不能虚构旧版本。

复查触发：接口/数据/栈变化、重复失败、事故、过期例外及项目约定的周期。规则没有适用范围、可执行检查或实际反馈价值时先澄清/裁剪；反复例外应复审规则或实现。维护者与复查周期依项目证据决定，不默认虚构负责人或期限。
